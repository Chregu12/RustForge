# RustForge — Vision Gap & Roadmap

_Generated audit of the current implementation against `Vision & Design Principles`. Grounded in the real `crates/` + `examples/` source (16 areas audited in parallel, then synthesized)._

## Verdict

RustForge is a convincing facade over a half-real engine: roughly 30-40% of the vision is genuinely working, but the parts that match the vision most closely are disproportionately the fake ones. The DX sugar (facades, macros) is frequently mounted on mock backends — routing's build_router() returns an empty Router, the Model/DB facade's query builder returns Ok(vec![]), Storage/Cache/Mail facades write to in-memory HashMaps while real S3/Redis/SMTP engines sit unwired one crate away, and auth keeps a single process-global current_user (a real cross-request security bug). Meanwhile several engines are genuinely strong (rf-orm SeaORM, rf-jobs, rf-ai's Anthropic provider, lettre mail, JWT extractor). The single most important strategic rule: engine before sugar — every hour spent making a macro prettier on top of a mock backend is negative work, because it deepens the "documented API returns empty data" trust debt that already runs through the codebase.

## Roadmap

## Honest verdict

RustForge today is best described as **a vision-shaped demo, not a working framework**. The Laravel-like surface is real Rust that compiles and often type-checks nicely, but a large fraction of the highest-fidelity surfaces are decoupled from their real engines:

| Symptom | Evidence |
|---|---|
| Routing facade doesn't serve traffic | `GlobalRouter::build_router()` returns empty `Router::new()`; handler string arg is `_handler`, discarded |
| Model/DB facade returns fake data | `rf-db-facade::QueryBuilder::get()` → `Ok(vec![])`, real `rf-orm` (SeaORM) not bridged |
| Storage/Cache/Mail facades are mocks | in-memory `HashMap` / hardcoded `MemoryMailer` / hardcoded `MemoryCache`, real S3/Redis/SMTP unwired |
| Auth is a security bug | one process-global `static GLOBAL_AUTH` `current_user` shared across all requests |
| Several advertised macros don't compile | `event!`/`dispatch!` (arity), `job!` (references nonexistent `rf-job-facade`), `mailable!`/`send_mail!`/`view!`/`back!` (nonexistent types/methods) |

**Strategic rule for the whole roadmap: engine before sugar.** Do not ship or polish DX on top of a mock backend. Where a facade already exists over a fake engine, the correct next commit is almost always "wire it to the real engine," not "add a prettier macro." Also delete or fix documented-but-broken macros immediately — they are pure trust debt.

### Rust feasibility limits (apply to every tier)

- `Controller@index`, top-level `controller Name { store() {} }`, `class Post { ... }`, `middleware(auth){ ... }`, bare `where(title=="x")`, `5.mb` — **none are valid Rust** outside a function-like macro's own token stream. Anything vision-literal requires macro-wrapping and loses IDE highlighting/goto-def inside the macro body.
- **`.` vs `::`**: static calls must be `Post::all()`, `SendInvoice::dispatch(order)`, `Mail::to(...)`. Bare-dot on a type is impossible; `SalesCoach.prompt(...)` only works if `SalesCoach` is a *value* (unit-struct/const), tripping `non_upper_case_globals`.
- **async hiding** is achievable (autoref-specialization + `#[auto_await]`) but obscures rust-analyzer types and is name-list-driven (unsound: a user's sync `find` gets awaited). **Result/Option/Ok/Err hiding is essentially unsolved** — auto-injecting `?` needs one uniform error type; mixed `String`/custom errors force lossy `anyhow`.
- **sync-over-async facades** (`Storage::put`, `Cache::remember`, `Mail::send`) using `Handle::block_on` **panic inside a running Tokio worker** (i.e. inside every axum handler). The only safe "no visible await" bridge is a dedicated runtime thread + channel, which adds hidden latency and stringly-typed errors.
- **bare property `post.user`** for lazy relations is impossible (no getter overloading, field read can't be async/Result). Only eager-hydrated `Option<User>` fields can look like property access.
- **ambient `request`/`user()`/`file()`** need a `tokio::task_local` set by middleware; calling them outside a request is a runtime failure, the opposite of Rust's compile-time guarantees.

## Tier 1 — Quick wins (engine real, high DX, low risk)

Ship these first; they convert already-working engines into vision-shaped surface with little risk.

| Area | Work | Why cheap |
|---|---|---|
| **queue** | Global `Queue` facade over container + `#[derive(Job)]` emitting `SendInvoice::dispatch(order)`; **fix the broken `job!` macro** (`rf-job-facade` → `rf-jobs`) | rf-jobs engine (batch/chain/DLQ/scheduler) is **real**; only the sugar/facade is missing |
| **events** | Single `pub fn event<E: Event>(e)` + `#[derive(Event)]` (auto `name()`/`as_any()`); **delete or fix `event!`/`dispatch!`**; collapse 3 dispatchers to 1 | 3 real dispatchers already exist; free-fn syntax is valid Rust, no proc-macro needed |
| **cache** | `DurationExt` giving `5.minutes()` (not `.min()` — collides with `Ord::min`); `cache!(remember: k, ttl, { block })`; **wire GLOBAL_CACHE to CacheConfig** so Redis/db drivers actually run; fix `block_on`-in-async | Already rated **strong**; mostly ext-trait + config wiring |
| **validation (non-file part)** | New `validate!{}` function-like macro with type-prefix (`string.max(255)`→MaxLengthRule, `int.min(18)`→MinRule), emitting the existing `HashMap<&str, Vec<Box<dyn Rule>>>` | String/numeric/date engine is **real** (48 rules); type-prefix fixes a **latent shipped correctness bug** where `min(8)` compiles as numeric not length |

**Do not** carry the `rules!` numeric-vs-length collision into `validate!`. Migrate off it; don't inherit the bug.

## Tier 2 — Flagship vertical slices (prove the vision end-to-end)

Pick **one** CRUD story and make it real all the way through. This is what turns "demo" into "framework." Recommend the **blog post CRUD slice** because it exercises the most vision surface at once.

**Slice A — "A real request creates a real row" (highest priority)**
Chain: `routes! get("/posts", PostController::store)` → controller with populated `request` → `validate!{}` → `Post::create({...})` hits a **real DB** → `view("posts.index")` / `json(post)`.

Requires, in order: (1) routing that serves (Tier 4), (2) models bridged to rf-orm (Tier 4), (3) request-body middleware populating `Request.fields`, (4) real `view()`/`json()` responses. When this one path is real and magical, the vision is *proven*; everything else is replication.

**Slice B — Validation + field inference + model as one declaration**
`#[derive(Model)]` that reads field *types* → emits SeaORM entity + columns + a companion input DTO + a seeded `Validate` impl (non-`Option` ⇒ required, `String` ⇒ string, `Option<T>` ⇒ nullable). This is the "one bare `title` means five things" vision and is **derive-macro-reachable** since types are visible — but only worth building **after** the DB engine underneath is real, else the "DB column" facet stays fake.

**Slice C — AI agent (differentiator, engine mostly real)**
`agent!{ SalesCoach, system="..." }` (unit-struct value) + `prompt().attachment(file(...)).run()`. Provider is a **real** reqwest POST. Only missing engine piece: `ContentBlock::Image/Document` + base64 `file()` — additive. Highest DX-win-per-effort of any area and a genuine Laravel-doesn't-have-this hook. Accept `::run().await?` — don't fight Result hiding.

## Tier 3 — Hard bets / research (serious IDE/type/error-handling risk)

Do **not** block the framework on these. Timebox or explicitly defer.

| Bet | Verdict |
|---|---|
| Hiding `Result`/`Ok`/`Err`/`Some`/`None` | **Research.** Needs body-rewriting proc-macro injecting `?` + `Ok(...)` wrap, requires one uniform error type. High chance of confusing errors pointing at generated code. Recommend: hide `.await` only, keep `?` visible. |
| Top-level `controller`/`class`/`middleware(auth){}` keywords | **Only via function-like macro.** Achievable syntactically but kills IDE highlighting/goto-def inside the body and makes `Request` a synthetic binding users can't retype. Recommend `::`-based real impls over literal fidelity. |
| String routing facade (`"HomeController@index"`) | **Dead end — abandon.** No type info, typos become runtime 404s, decoupled from axum. Promote `routes!{}` with `Controller::method` tokens instead. |
| Bare `post.user` lazy relation | **Impossible for lazy.** Standardize on `.user().get(&db).await?`; offer bare access only via eager-hydrated `Option<User>` fields. |
| Ambient `request()`/`user()`/`file()` free fns | **Feasible but footgun-y.** task_local set by middleware, owned returns (clone cost), runtime panic if called outside a request. Ship, but document the sharp edge. |

## Tier 4 — Fix-the-engine-first (mock/partial — MUST precede any sugar)

These block the flagship slices. **This is the real work of the project.**

| Area | Engine defect | Fix | Priority |
|---|---|---|---|
| **auth** | `static GLOBAL_AUTH` = cross-request auth bleed (**security bug**) | Move to `task_local`/request-extensions set by middleware; wire the real JWT `get_claims` path to the facade | **P0 (security)** |
| **routing** | `build_router()` returns empty Router; handler arg discarded | Promote `routes!{}` to canonical; expand to real `axum::routing::get(Controller::method)`; delete the string facade | **P0 (blocks Slice A)** |
| **models / DB** | `QueryBuilder::get()` → `Ok(vec![])` over mock `DBManager`; two parallel ORMs | Bridge facade `Model` to **real rf-orm** (or give facade a real connection); unify the two stacks | **P0 (blocks Slice A/B)** |
| **storage** | sync facade → `HashMap`; `disk("s3")` no-op; real Local/S3 unwired | Replace HashMap with backend enum delegating to real async `Storage`; bridge async→sync via runtime-thread + channel (not `block_on`) | P1 |
| **responses** | `download()` returns literal `"File content from: <path>"`; `back()` always `/`; ViewFacade stub; `view!`/`back!` don't compile | Real file read + mime; read Referer for `back()`; pick **one** view crate; fix/delete broken macros | P1 |
| **mail** | facade hardcoded `MemoryMailer`; `block_on` panic; `mailable!`/`send_mail!` reference nonexistent types | Wire facade to configurable `MailManager` (engine is real/lettre); add `Recipient` trait for `to(user)`; fix/delete macros | P1 |
| **validation (file)** | no `ImageRule`/`MimeRule`/`FileSizeRule`; rf-upload `max_size` unwired | Build the missing rule engine + wire `UploadedFile`; require `mb(5)` not `5.mb` | P1 |
| **request_helpers** | multipart never parsed (`file()` empty), no ConnectInfo (`ip()`), no cookie parse, `user()` always None | Parse multipart in FromRequest; capture `ConnectInfo`; parse Cookie header; real auth middleware | P1 |
| **field inference** | `unique`/`exists`/`required_if` derive rules are `assume passes` stubs | Implement async DB validation pass with a live connection (depends on models P0) | P2 |
| **relationships** | `HasRelationships::load_*` are `panic!` stubs; `#[relations]` discards method bodies (latent bug); relation structs are dead metadata | Delete/complete stubs; make `#[relations]` generate real `.user()`/`.posts()` accessors over the working rf-orm builders | P2 |

## Recommended sequence

1. **Delete/fix every non-compiling advertised macro** (`event!`, `dispatch!`, `job!`, `mailable!`, `send_mail!`, `view!`, `back!`) and soften docs. — Stops actively lying to users; near-zero cost, immediate trust repair.
2. **Fix auth global-static → per-request state.** — It's a real security vulnerability, not just a DX gap; must not ship as-is.
3. **Make routing serve real traffic** (`routes!{}` → real axum handlers; delete empty `build_router` + string facade). — Unblocks every request-driven feature.
4. **Bridge the model/DB facade to real rf-orm and unify the two ORMs.** — Kills the biggest "returns empty data" lie and unblocks the flagship slice.
5. **Add request-body/multipart middleware populating `Request.fields`** (+ `ip`/`cookie`/`file`). — Makes implicit `request` accessors and `file()` real, feeding validation and controllers.
6. **Ship `validate!{}` with type-prefix + file-validation engine.** — High DX, fixes the latent length-vs-numeric correctness bug; now has a real request to validate.
7. **Land flagship Slice A (request → controller → model → response) as a real example** and dogfood it (the current `phase12-blog` still writes raw `.await`/`Result`). — Proves the vision end-to-end; becomes the reference app.
8. **Tier-1 quick wins in parallel** (queue facade, events `#[derive(Event)]`, cache `DurationExt`+backend wiring). — Independent, cheap, real engines already there.
9. **Wire storage/mail/cache facades to real backends** (runtime-thread bridge, not `block_on`). — Removes the mock-HashMap trio.
10. **`#[derive(Model)]` field inference (Slice B)** on top of the now-real DB. — The "zero-config bare field" magic, safe only after step 4.
11. **AI agent slice (Slice C)** — attachments engine + `agent!`/`prompt().run()`. — Differentiator; low dependency on the rest.
12. **Relationship accessor generation; make `#[relations]` real.** — After models are real; standardize on `.relation().get(&db).await?`.
13. **Defer/timebox the hard bets** (Result/Option hiding, literal top-level keywords, bare `post.user`). — Explicitly decide "good enough `::`/`.await?` ergonomics" rather than chasing impossible fidelity.

**One-line meta-rationale:** steps 2-5 are pure engine truth-telling and unblock everything; only after a request can really reach a real row does adding sugar (6-12) create value instead of debt.

## Per-area detail

### validation

- **Maturity:** partial · **Engine:** real · **Feasibility:** moderate · **Effort:** L · **DX win:** high
- **Today:** Three real, working paths, none matching the vision's typed fluent DSL. (1) rules!{} function-like proc-macro (crates/rf-macros/src/rules_macro.rs) with PIPE syntax: rules! { email: required | email, password: required | min(8) | max(72), age: integer | between(18,120) } -> expands to HashMap<&'static str, Vec<Box<dyn rf_validation::Rule>>>. Verified compiling in examples/laravel-syntax-simple/src/main.rs. (2) Attribute derive #[derive(ValidateDerive)] (rf-validation-derive) with #[validate(required, email, max = 255)] / #[validate(unique = "users")] -> real generator emits a Validate impl. (3) Imperative Validator::new(data).rules(...).validate().await plus RulesBuilder::new().add("email", vec![Box::new(RequiredRule), Box::new(EmailRule)]).build(). Also ValidatedJson<T> axum extractor.</current_syntax>
validate! { title: string.max(255), email: email, age: int.min(18), image: image.optional.max(5.mb) } — typed fluent DSL with type-prefix and dot method chains, never Laravel pipe-strings
- **Gap:** No validate!{} macro exists; the closest thing, rules!{}, uses `|` pipes not `.` chains and has NO type-prefix. The type-prefix (string/int/email/image) is exactly what disambiguates length-vs-value, and it is unrepresentable today: rules! does a naive capitalize(name)+"Rule" mapping, so max(255) ALWAYS resolves to numeric MaxRule::new(255) (compares f64), NEVER MaxLengthRule. The shipped example password: required | min(8) is therefore semantically wrong (validates numeric value>=8, not length>=8). File/image validation is ENTIRELY missing: grep of crates/rf-validation/src/rules yields no ImageRule/FileRule/MimeRule/SizeRule (only 48 string/numeric/date/array/database/conditional rules). rf-upload/src/lib.rs has a max_size config field but no Rule wiring, so image.optional.max(5.mb) has zero backing engine. The .optional fluent modifier is not expressible in rules! (only the derive path handles it via Option<T>+nullable). The 5.mb byte-size literal is not a valid single Rust token.</gap>
Add a NEW function-like proc-macro validate!{} in rf-macros with custom token parsing (do not overload rules!, whose pipe grammar is load-bearing). Parse field: TYPE.method(args).method(args) where TYPE (string/int/email/image/bool/date/array) selects the correct rule family, so string.max(255)->MaxLengthRule and int.min(18)->MinRule, resolving the collision at parse time. Emit the same HashMap<&str, Vec<Box<dyn Rule>>> the existing real Validator consumes, reusing the engine as-is. For image/file: build the missing engine first (add ImageRule/MimeRule/FileSizeRule under crates/rf-validation/src/rules and wire rf-upload's UploadedFile through them); .optional maps to omitting RequiredRule. Rust token limits to flag: 5.mb does not lex as one token (5. is a float literal, then mb ident), so require mb(5), 5.megabytes(), or a size!(5 mb) helper; bare string/image idents are legal only inside the macro body, never top-level. Since Validator::validate is async and UniqueRule/ExistsRule do DB IO, keep validate! producing the sync rules map and let callers .await; fully hiding .await will fight rust-analyzer and Send bounds.
- **Risks:** 1) The rules! numeric-vs-length collision is a latent correctness bug already shipped in examples; migration must not silently inherit it. 2) Hand-rolled dot-chain + 5.mb parsing gives poor rust-analyzer completion/inference inside the macro body (opaque idents, no checking of field names against a struct). 3) Custom-parser error messages are worse than derive-attribute diagnostics; malformed chains yield cryptic spans. 4) Real image validation needs byte/MIME sniffing (IO), not just sugar. 5) Async/Result propagation: masking .await risks Send/lifetime surprises with async DB rules. 6) Maintenance: a third validation front-end (derive + rules! + validate!) grows surface; consider deprecating rules! rather than keeping three.
- **Key files:** `crates/rf-macros/src/rules_macro.rs`, `crates/rf-macros/src/lib.rs`, `crates/rf-validation/src/validator.rs`, `crates/rf-validation/src/rules/string.rs`, `crates/rf-validation/src/rules/numeric.rs`, `crates/rf-validation/src/form_request.rs`, `crates/rf-validation-derive/src/generator.rs`, `crates/rf-upload/src/lib.rs`

### controllers

- **Maturity:** partial · **Engine:** partial · **Feasibility:** moderate · **Effort:** L · **DX win:** medium
- **Vision:** controller PostController { store() { } } — `request` implicitly available in every method, no explicit Request parameter
- **Today:** Closest today is an attribute macro on a normal impl block: `#[controller] impl UserController { pub fn index(_request: Request) -> ResponseBuilder { ... } }` (see examples/macros-demo/src/main.rs:41-73). The macro `controller_impl` (crates/rf-macros/src/controller_macro.rs:11-55) only (a) forces every `pub fn` to `async` and (b) runs `AwaitTransformer` to auto-insert `.await`. The `Request` must still be declared explicitly as a parameter; it is NOT injected. `Request` itself is real: crates/rf-request/src/request.rs wraps an axum `HttpRequest<Body>` with a `fields: HashMap<String,Value>` and `get`/`require`/`validate` methods. rf-routing has a real `ControllerAction` enum + `ControllerRegistry` (crates/rf-routing/src/controller.rs) for RESTful mapping.
- **Gap:** Two gaps. (1) Syntax: the vision `controller Name { store() {} }` is not valid Rust — `controller` cannot be a top-level keyword and method bodies without `fn`/param lists won't parse. The current form is a decorated standard `impl` block, not a custom DSL. (2) Behavior: `request` is not auto-available — every method still takes an explicit `_request: Request` param. Also, the crate-level doc (crates/rf-macros/src/lib.rs:10) and the `#[controller]` premise imply "automatic route registration," but the macro does NO registration — it emits the impl unchanged apart from async/await. Route wiring is still fully manual (`routes!{ post "/posts" => post_controller::store }`, laravel_macros.rs). Field population of `Request.fields` is done externally via `with_fields`; there is no body-parsing middleware shown, so `request.get(...)` returns empty unless a caller pre-fills it.
- **Approach:** Replace/augment the attribute macro with a function-like proc-macro `controller!{ PostController { store() {...} } }` that parses the sugar (custom syn parser: an ident + a brace group of `ident(args?) { block }` items) and expands to a real `struct` + `impl` where each method gains a synthesized `request` binding. Implicit `request` is best done by macro-injecting a hidden parameter and shadowing it with `let request = ...;` at the top of each body (compile-time, keeps rust-analyzer type info), rather than a task-local (which loses types and complicates borrows). Auto-registration should be added by having the macro emit an inventory/`ctor`-style registration or a generated `fn routes() -> Router` so the "automatic" claim becomes real. Keep the existing `AwaitTransformer` prelude reuse. Engine work needed: real request-body/query parsing middleware to populate `Request.fields` so implicit `request.get()` is not empty.
- **Risks:** Hiding the `Request` param via macro injection means rust-analyzer sees a synthetic binding — go-to-def and error spans can be confusing, and users can't name a differently-typed request (e.g. FormRequest) without an override syntax. Method signatures returning `ResponseBuilder`/`Result` still surface async+Result to the router; the auto-await transformer is heuristic (visits only top-level Expr/Local stmts in controller_macro.rs:41-49) so `.await` insertion can miss nested/branch expressions, producing surprising compile errors. Task-local alternative would break `Send`/borrow across `.await`. The current doc overclaims "automatic route registration" (lib.rs:10) — leaving it unimplemented is a correctness/trust risk. Custom-keyword DSL also breaks IDE syntax highlighting inside the macro body.
- **Key files:** `crates/rf-macros/src/controller_macro.rs`, `crates/rf-macros/src/function_macro.rs`, `crates/rf-macros/src/await_transformer.rs`, `crates/rf-macros/src/lib.rs`, `crates/rf-request/src/request.rs`, `crates/rf-routing/src/controller.rs`, `examples/macros-demo/src/main.rs`

### routing

- **Maturity:** partial · **Engine:** mock · **Feasibility:** hard · **Effort:** L · **DX win:** high
- **Vision:** get("/", HomeController@index); post("/posts", PostController@store); middleware(auth) { ... }
- **Today:** Two disjoint paths exist. (1) The Laravel-look facade: `Route::get("/", "HomeController@index")`, `Route::post("/users","UserController@store").name("x").middleware("auth")`, and `Route::group().prefix("/api").middleware("auth").routes(|g| { g.get("/users","UserController@index"); })` / `Route::middleware(&["auth"]).add(Route::post(...))` (crates/rf-routing/src/facade/route.rs). (2) The macro path that ACTUALLY serves traffic: `routes!{ GET "/" => home_handler, POST "/users" => users_store }` which expands to axum `router.route(path, get(handler))` (crates/rf-routing/src/macros.rs), plus `resource!("posts")`, `group!{prefix:..,middleware:[..],routes:{..}}`, `middleware!{"auth"=>handler}`. Real apps (examples/auth-demo, phase12-blog, hello, htmx-livewire-alternative) bypass all facades and write raw `Router::new().route("/", get(home))`.
- **Gap:** The facade that matches the vision (`Route::get("/","HomeController@index")`) is metadata-only and does NOT serve requests. The handler string arg is literally discarded — signature is `fn get(path, _handler: impl Into<String>)` (facade/route.rs:48), the `_` prefix proving it is unused. `GlobalRouter::build_router()` explicitly returns an empty `Router::new()` with the comment "This is a placeholder that returns an empty router" (facade/registry.rs:119-130). There is NO controller-dispatch layer: nothing resolves the "HomeController@index" string to an axum handler. The `#[controller]` attribute macro (controller_macro.rs) only makes methods async + auto-awaits; it registers no routes. The example itself is captioned "Route facade (registration only)" (laravel-syntax-simple/src/main.rs:7,101) and merely prints a route count. So the closest-to-vision API is a fake for real HTTP. Separately: vision `get(...)` is bare/unprefixed (needs `Route::`), `Controller@index` (no quotes) is not valid Rust in call position, and `middleware(auth){...}` is a top-level block that cannot exist as free Rust. URL-generation / named routes / signed URLs ARE real and tested (named_routes.rs, signed_urls.rs, lib.rs tests pass).
- **Approach:** Do not chase the string-facade; it is architecturally a dead end (no type info, typos become runtime errors, and it is decoupled from axum). Instead promote the working `routes!{}` function-like proc-macro to the canonical API and give it vision-shaped tokens: parse `get("/", HomeController@index)` / `post("/posts", PostController::store)` and expand each arm to `.route(path, ::axum::routing::get(HomeController::index))`, where controller methods are plain `async fn`s (real axum handlers with extractors). This keeps compile-time checking, IDE go-to-def, and real serving. macro_rules CAN match `@` as a literal token, but robust `Controller@method` + a `middleware(auth){ ... }` block need a function-like proc-macro with custom syn parsing (a la existing rules!/model! macros) expanding the block to `.route_layer(from_fn(auth))`. Then delete/replace the empty `build_router()` placeholder so the facade's registered routes actually mount, OR drop the facade entirely. Engine work required: a controller trait whose methods are handler fns, plus middleware-name→layer resolution wired into axum (the middleware_pipeline.rs registry exists but is not connected to any live router).
- **Risks:** Hiding axum handlers behind `Controller@method` string sugar breaks rust-analyzer (no autocomplete, no type inference on extractors, no jump-to-def) and turns handler typos into runtime 404s — the current facade demonstrates exactly this failure. Using `::` instead of `@` (i.e. `HomeController::index`) preserves IDE support at the cost of literal vision fidelity; recommend that. Async/Result hiding via macros collides with axum's `Handler` trait bounds — controller methods must still return `impl IntoResponse`, so error propagation (`?` / Result→Response) needs an explicit response-mapping shim or it will surface as opaque trait-bound errors. Maintaining a second parallel router (facade metadata store + real axum tree) invites drift; consolidate to one. Middleware `auth` resolution from a bare ident requires a global registry, reintroducing runtime-lookup fragility.

(d) Fix the runtime-nesting hazard: detect an existing tokio handle (`Handle::try_current`) or provide async facade variants, instead of a private Runtime + block_on.
- **Risks:** block_on-inside-async panic is the biggest correctness risk for real web handlers. Hiding `CacheResult` behind panic-on-error would break error propagation and surprise users; keeping `?` diverges from the infallible-looking vision. `5.min()` ext trait may collide with `Ord::min` on integers (method-resolution ambiguity) — name it `.minutes()` to be safe. Backend-from-config wiring touches global state init order. Deserialize turbofish (`Cache::get::<T>`) still leaks type annotations that the vision hides; rust-analyzer inference is fine but the macro get-path returns a bare Result the caller must annotate.

### queue

- **Maturity:** partial · **Engine:** real · **Feasibility:** moderate · **Effort:** M · **DX win:** high
- **Vision:** SendInvoice.dispatch(order); SendMail.dispatch(user)
- **Today:** Real, working path is instance-based on a QueueManager handle. rf-jobs: `let manager = QueueManager::new("redis://...").await?; manager.dispatch(job).await?` (also `dispatch_to`, `dispatch_later`, `dispatch_on`, `dispatch_with_priority`). Sync wrappers exist in `crates/rf-jobs/src/api.rs`: free fn `dispatch(&manager, job)` and `SyncQueueManager::dispatch(job)` (both `block_on`). Fluent builders: `JobChain::...dispatch(&manager).await` and `JobBatch::...dispatch(&manager).await`. rf-queue is a parallel duplicate engine with `Arc<dyn Queue>` + `dispatch(queue, job)`. The `rf-macros` `job!{}` macro advertises `SendEmail::new(...).dispatch().await?` in its doc comment but does NOT match the vision and is broken (see engine_status).
- **Gap:** Vision wants a static, container-resolved dispatch on the job type with no visible queue handle (`SendInvoice.dispatch(order)`). Today every dispatch requires an explicit `QueueManager` value threaded through. There is no `Dispatchable`/facade layer that resolves a global queue from the container, and no derive that puts a static `dispatch(...)` on the job type. Two hard-syntax gaps: (1) Rust requires `SendInvoice::dispatch(order)` not `.` ; (2) in the vision `order` is a constructor arg (Laravel `SendInvoice::dispatch($order)` builds+queues the job), which needs a generated constructor+dispatch pair. The one macro that gestures at this — `job!{}` in `crates/rf-macros/src/helpers.rs` (job_impl ~L1720) — generates `impl rf_job_facade::Job for #name`, but NO crate named `rf-job-facade` exists in the workspace (grep of all Cargo.toml finds nothing) AND it never emits a `.dispatch()` method despite the doc claiming one. So that sugar is non-compiling vaporware.
- **Approach:** Two pieces. (1) Global queue facade: register a `QueueManager` in the service container at boot (rf-container exists) and expose a `Queue` facade / `OnceCell`-backed global, mirroring the existing `block_on` sync pattern in api.rs. (2) Derive macro `#[derive(Job)]` (or extend the `job!{}` proc-macro after fixing its broken `rf_job_facade` reference to `rf_jobs`) that emits an inherent `impl Type { pub fn dispatch(args) -> JobId { GLOBAL_QUEUE.dispatch(Self::new(args)) } }` plus a blanket `Dispatchable` trait giving `job.dispatch()`. Net achievable API: `SendInvoice::dispatch(order)` (colon-colon) — the closest legal Rust to the vision. The bare-dot `SendInvoice.dispatch(order)` is impossible outside a function-like macro; only `::` works for a static call. Register the type in JobRegistry automatically via `inventory`/`ctor` so workers can deserialize without manual `registry.register::<T>()` (currently manual in examples/jobs-demo).
- **Risks:** block_on-based sync dispatch panics if called from inside an existing Tokio runtime (nested runtime) — must document/guard or keep dispatch async, which then leaks `.await` and `Result` into user code (vision hides both). A global mutable queue facade hurts testability and type-inference clarity (rust-analyzer sees a macro-generated static method, weaker jump-to-def). Auto-registration via linker tricks (`inventory`/`ctor`) is fragile across platforms and with dead-code stripping. Also: two competing engines (rf-queue vs rf-jobs) must be reconciled first or the facade will bind to the wrong one; rf-jobs is the mature one (batch/chain/routing/scheduler/DLQ). The `job!` macro is currently shipping broken and should be fixed or removed to avoid a documented-but-nonfunctional API.
- **Key files:** `crates/rf-jobs/src/queue.rs`, `crates/rf-jobs/src/api.rs`, `crates/rf-jobs/src/worker.rs`, `crates/rf-jobs/src/registry.rs`, `crates/rf-jobs/src/job.rs`, `crates/rf-jobs/src/routing.rs`, `crates/rf-macros/src/helpers.rs`, `crates/rf-macros/src/lib.rs`

### events

- **Maturity:** partial · **Engine:** partial · **Feasibility:** moderate · **Effort:** M · **DX win:** medium
- **Vision:** event(UserCreated { user })
- **Today:** Closest real, working call today is the free function in rf-global-helpers: `event(&user_event)` where `UserCreated` manually implements the crate's `Event` trait (`fn name(&self)->&str { "user.created" }` + `fn as_any(&self)->&dyn Any { self }`), plus `listen("user.created", |e| {...})`. Also real: `rf_event_facade::Event::dispatch("user.created", data)?` (string name + serde_json, sync) and `rf_events::EventFacade::dispatch(name, data)?`. The advertised sugar `event!(UserCreated { user_id: 123 })` and `dispatch!(user.registered, user_id = 1)` do NOT compile (see gap).
- **Gap:** To reach `event(UserCreated { user })` verbatim: (a) fix/replace the broken `event!`/`dispatch!` macros or drop them in favor of the free fn; (b) the working free `event()` takes `&E` (needs `&`) and requires a hand-written `Event` impl with a hardcoded string name and `as_any` — vision wants pass-by-value with auto-derived identity; (c) consolidate the three competing engines (sync name-keyed x2, async TypeId-keyed x1) so a listener registered one way actually receives events dispatched another; (d) decide name derivation (currently manual string vs type_name). Engine reality: three REAL, tested dispatchers exist (none is a mock) but the sugar meant to match the vision is broken — the `event!` macro at crates/rf-macros/src/helpers.rs:1166 expands to a ONE-arg `rf_event_facade::Event::dispatch(#event)` while that fn requires TWO args `(event_name:&str, data:T)` (facade.rs:67); `dispatch!` (helpers.rs:1590) has the same one-arg defect. No example uses either macro.
- **Approach:** The vision syntax is VALID Rust as-is — `event(UserCreated { user })` is just a function call, so NO function-like proc-macro with custom token parsing is needed. Best path: (1) keep a single `pub fn event<E: Event>(e: E)` (by value) as the public entry; (2) add a `#[derive(Event)]` derive macro auto-implementing `name()` (from type_name or `#[event(name=...)]`) and `as_any()`, killing the manual trait boilerplate; (3) unify on ONE dispatcher (the sync global for no-await DX, or the async TypeId engine if async listeners are required) and delete the redundant two; (4) fix or remove the broken `event!`/`dispatch!` macros so they route to the same engine. Struct field shorthand `{ user }` is native Rust struct-literal syntax — no macro required. Dispatch should stay infallible (the global helper already is) so the un-`?`'d vision call is clean.
- **Risks:** Three redundant real engines create a silent-no-op trap: a listener on rf-events (async TypeId) never fires for an event sent via rf-global-helpers (sync name) — events appear lost. type_name-based routing is fragile across module/crate renames. The async rf-events engine can't be hidden behind a sync `event()` without a runtime handle; async listeners in the sync path are impossible. rust-analyzer sees a plain fn (good) but `#[derive(Event)]` errors surface at the derive site. The currently-broken `event!`/`dispatch!` macros are documented as working in rf-macros/src/lib.rs — a trust/correctness risk until fixed or removed.
- **Key files:** `crates/rf-global-helpers/src/event.rs`, `crates/rf-event-facade/src/facade.rs`, `crates/rf-event-facade/src/manager.rs`, `crates/rf-events/src/lib.rs`, `crates/rf-events/src/facade.rs`, `crates/rf-macros/src/helpers.rs`, `crates/rf-macros/src/lib.rs`

### mail

- **Maturity:** partial · **Engine:** partial · **Feasibility:** moderate · **Effort:** M · **DX win:** medium
- **Vision:** Mail.to(user).send(WelcomeMail)
- **Today:** Two real paths exist. (1) Verbose, actually-working path (used in examples/mail-demo/src/main.rs): implement `impl Mailable for WelcomeEmail { fn build(&self) -> MailBuilder {...} }` then `welcome.send(&mailer).await?` where `mailer` is a concrete backend. (2) Laravel-style facade in crates/rf-mail/src/facade.rs (re-exported as `rf::Mail`): `Mail::to("user@example.com").send(welcome_mailable)?` — synchronous, no `.await`. The `mailable!` and `send_mail!` proc-macros are documented (rf-macros) with target syntax `Mail::to(...).send(WelcomeEmail { user }).await?` but DO NOT COMPILE (see gap).

Behavior gaps are the real problem: (a) the facade's `GLOBAL_MAILER` is a HARDCODED `MemoryMailer` (facade.rs L29-31), so `Mail::to(..).send(..)` never delivers real mail — it only stores in memory. (b) The facade uses `block_in_place`+`Handle::current().block_on` which panics on a current-thread runtime. (c) The sugar macros are broken dead code: `mailable!` (rf-macros/src/mailable_macro.rs) generates references to `rf_mail::Envelope`, `Content`, `Headers`, `PendingMail` and `Message::new().envelope()...` — NONE of these types/methods exist in rf-mail (grep confirms zero hits); it also calls `.send(self).await` on the sync facade. `send_mail!` (helpers.rs L1538) generates `rf_mail_facade::Mail::new().to().subject().body().send()` — the facade `Mail` struct has none of `new/subject/body/send()`-no-arg. Neither macro is used in any example.
- **Approach:** The engine (lettre-backed SMTP in backends/smtp.rs, plus memory/log/mock/ses/mailgun/postmark/sendgrid, the `Mailable` trait, and `MailManager` driver dispatch) is genuinely real, so this is mostly plumbing, not engine work. Steps: (1) Wire the facade to a configurable global `MailManager` instead of a hardcoded `MemoryMailer`, with a `Mail::fake()`/set-driver mechanism so `Mail::to().send()` actually delivers via the configured driver. (2) Introduce a `Recipient`/`ToAddress` trait implemented for `&str`, `String`, `Address`, and user models (derive or blanket) so `Mail::to(user)` works — closing the `to(user)` gap. (3) Keep `Mail::to(x).send(mailable)` as the canonical form; accept that `.` and bare-type `WelcomeMail` are not valid Rust — document `Mail::to(user).send(WelcomeMail::new(..))`. (4) Either fix or DELETE the `mailable!`/`send_mail!` macros; if kept, rewrite `mailable!` (a function-like proc-macro is the only way to allow the `struct + fn envelope/content` block syntax) to emit the REAL `impl Mailable { fn build(&self)->MailBuilder }` and drop the nonexistent Envelope/Content/PendingMail types. A `#[derive(Mailable)]` with `#[mail(subject=..., view=...)]` attrs would be the cleanest, most rust-analyzer-friendly option.

- **Maturity:** partial · **Engine:** partial · **Feasibility:** moderate · **Effort:** L · **DX win:** high

- **Today:** Closest today (async, Result-typed, no named agents, no attachments): `let provider = AnthropicProvider::new(key); let req = ChatRequest::default_model().system("...").message(Message::user("Analyse this transcript")); let resp = provider.chat(&req).await?; resp.text()`. ### async_hiding

- **Maturity:** partial · **Engine:** partial · **Feasibility:** hard · **Effort:** L · **DX win:** medium
- **Vision:** Developer rarely sees async/await/Result/Option/Ok/Err/Some/None — all wrapped internally
- **Today:** `#[auto_await] async fn handler() -> Result<..> {..}` and its alias `#[await_calls(fetch, charge)] / #[auto_await(also("m"))]`; also the function-like `rustforge!{ ... }` block which auto-injects `#[auto_await]` per fn and honors a `#[sync]` opt-out marker. Under the hood each matched call is rewritten to `(&__rf_w(EXPR)).__rf_resolve().await` (autoref specialization: awaits futures, passes plain values through), and a plain `fn` is auto-promoted to `async fn`. Matched names are a hardcoded allow-list (find/all/create/save/get/put/attempt/validate/... in await_transformer.rs).
- **Gap:** Only async/await is hidden. Result/Ok/Err/Some/None are NOT hidden at all — proof is the macro's OWN passing test (crates/rf-macros/tests/auto_await_sync_async.rs): the handler still returns `Result<i64,String>`, writes `?` after every call, `Ok(...)` at the tail, and `cached.unwrap_or(0)`. No code path rewrites `?` (no syn Expr::Try injection anywhere) or normalizes return values into Ok/Err. So error propagation, Option unwrapping, and the `-> Result<..>` signature remain fully visible and mandatory. Secondary gaps: (1) the auto-await set is a static name list — a user method named e.g. `find` that is sync-and-fallible gets no special error handling and any non-listed async method needs manual `also(..)`; (2) the feature is not dogfooded — the shipped example examples/phase12-blog/src/main.rs still writes raw `.await`, `Result<>`, and `Ok(...)`; (3) the facades the sugar sits on (e.g. rf-db-facade manager.rs `select`/`insert`) are in-memory mocks explicitly commented "returns mock data", so even where async is hidden the data engine underneath is fake.
- **Approach:** Attribute proc-macros already exist and work: keep `#[auto_await]`/`#[await_calls(..)]` and the `rustforge!{}` function-like wrapper that auto-applies them. To hide Result/? the only viable path is a body-rewriting proc-macro that walks the fn AST and appends a synthetic `?` (syn Expr::Try) onto matched framework calls, plus wraps the return so a bare tail value/`return x` becomes `Ok(x)` — i.e. extend AwaitTransformer to also emit Try nodes and normalize the return type/expr. Hiding Some/None/Option requires a nullable value type or accessor sugar, not a macro over std Option. Cannot be a top-level keyword; must stay inside `#[auto_await]`/`rustforge!{}`. Autoref-specialization adapter (`__rf_resolve`) is the sound mechanism for sync-vs-async and should be preserved.
- **Risks:** rust-analyzer/type-inference: the `(&__rf_w(EXPR)).__rf_resolve().await` wrapper obscures types, hurting IDE hover/completion and producing confusing errors that point at generated adapter code, not user code. Name-based matching is inherently unsound — a user's sync helper sharing an allow-listed name (find, get, save, user, id, send) gets wrapped/awaited unexpectedly, and the list can silently drift from real facade signatures. Auto-promoting `fn`->`async fn` changes public signatures/trait-impl compatibility. Extending to hide `?`: auto-injecting Try requires the fn to return a compatible Result and a uniform error type across heterogeneous facade errors (String vs custom) — mixed error types will fail to compile or force a lossy `Box<dyn Error>`/`anyhow`, and a wrongly-injected `?` on a non-Result value is a hard error surfaced far from the source. Hiding Some/None can mask real null-handling bugs. Maintenance: the whole scheme is a growing hardcoded name registry with no compile-time link to the APIs it mirrors.
- **Key files:** `crates/rf-macros/src/await_transformer.rs`, `crates/rf-macros/src/lib.rs`, `crates/rf-macros/src/rustforge_block.rs`, `crates/rf-macros/tests/auto_await_sync_async.rs`, `crates/rf-db-facade/src/manager.rs`, `examples/phase12-blog/src/main.rs`

### Field-level inference: one bare `title` field → required + string + request field + DB column + validation target

- **Maturity:** partial · **Engine:** mock · **Feasibility:** moderate · **Effort:** L · **DX win:** high
- **Vision:** A bare `title` (e.g. `title: String` in a model) implicitly means: required, string type, an input/request field, a DB column, and a validation target — with no attributes at all.
- **Today:** Nothing infers rules from a bare field today; every facet is declared explicitly and in separate macros/structs:
- Validation: `#[derive(Validate)]` + per-field `#[validate(required, string, max = 255)]` (rf-validation-derive) — real codegen calling `rf_validation::validators::*`.
- Request+validation: `form_request!{ struct CreateUserRequest { #[required, email] email: String, ... } }` or `#[form_request]` (rf-macros/form_request_macro.rs) — generates struct + `impl FormRequest` whose `rules()` is built from the same attributes.
- Model/columns: `#[model]` (rf-model-macro) infers table name (pluralized), injects `id`/`created_at`/`updated_at`, maps `#[hidden]`→`#[serde(skip_serializing)]`; or `Model!(Post: title, body)` (rf-macros/simple_model.rs) which infers `String` type + `FILLABLE`/`HIDDEN` + timestamps for bare fields.
The single closest thing to the vision's "bareness implies something" is `Model!(Comment: body, user_id)`: a bare name infers type=String + column + fillable — but NOT required/validation, NOT a request struct.
- **Gap:** The vision unifies five facets from one bare token; today they are five separate, fully-declared things, and none are inferred from "bareness":
1. No type→rule inference. `title: String` does not imply `required`+`string`; you must write `#[validate(required, string, ...)]`. `Option<T>` vs `T` is respected only inside `#[derive(Validate)]` (generator.rs treats optional-not-required as skip-if-None), but that is not extended to auto-requiredness of non-Option fields.
2. Model, request DTO, and validation are three distinct declarations. No single field definition emits an entity column + an input field + a Validate impl together.
3. "DB column" is not real for the model macros. `#[model]`/`Model!` route static/query methods through `rf_db_facade::Model` → `rf_db_facade::QueryBuilder::get()` which returns `Ok(vec![])` (query_builder.rs:544) over a mock `DBManager` (manager.rs:33 "returns mock data"). A real SQLite engine exists but in a DIFFERENT crate (rf-orm/src/facade/db_manager.rs:78 uses rusqlite) and is not wired to these macros.
4. The DB-dependent validation rules are stubs. In rf-validation-derive/generator.rs `Unique`/`Exists`/`UniqueIgnore` emit `#[allow(unused_variables)] let _table = ...;` with a comment "assume validation passes"; `RequiredIf`/`RequiredUnless`/`RequiredWith` are likewise placeholders. So even the declared unique/exists "validation target" does nothing.
- **Approach:** Two-part: (A) inference in a proc-macro, (B) make the engine under it real.
(A) A derive `#[derive(Model)]` (or function-like `model!{}`) that reads field TYPES and emits all facets from a bare field: non-`Option<_>` ⇒ `required`; `String`/`&str` ⇒ `string`; numeric types ⇒ `integer`/`numeric`; `Option<T>` ⇒ `nullable`; then generate simultaneously (1) the SeaORM entity + column list (as `#[model]` does), (2) a companion input DTO `CreateXRequest`/`UpdateXRequest` (Rust cannot make one struct be both the persisted entity and a partial input — a generated companion is required), (3) a `Validate`/`FormRequest` impl seeded with the inferred rules, and (4) column metadata for migrations. Attributes remain as opt-in overrides (e.g. `#[max(255)]`, `#[unique]`). This is well within derive-macro reach since types are visible; a function-like `model!{}` is only needed if you want non-Rust column DSL sugar.
(B) Repoint the generated query/persistence layer from the mock `rf-db-facade` to the real `rf-orm` engine (rusqlite today, ideally a sqlx pool), and implement the async `unique`/`exists` path: thread a live connection into an async validation pass (the current derive is sync and its DB rules are no-ops — this is the load-bearing engine work).
- **Risks:** 1. Async/Result leakage: real `unique`/`exists` require a DB round-trip, so a synchronous `Validate::validate(&self)` cannot host them (that is exactly why generator.rs stubs them). A separate `async fn validate(db)` path must be generated and the sugar cannot fully hide `.await`/`Result`.
2. Type-inference / rust-analyzer: generating a hidden companion request struct + trait impls from a derive degrades go-to-definition and error locality; users see errors on synthesized idents.
3. Split-brain engines: two DB facades exist (`rf-db-facade` mock, `rf-orm` real). If inference lands but stays wired to the mock, the "DB column" facet remains fake — the framework's known "documented API returns empty data" pattern (get()→`Ok(vec![])`). Consolidation is a prerequisite, not optional.
4. Over-inference ambiguity: mapping `Option<T>`→nullable and `T`→required can surprise (e.g. bool defaults, foreign-key ids), and length/precision cannot be inferred from Rust types, so `max`/DB varchar sizing still needs attributes — the "zero config" promise is only partial.
- **Key files:** `crates/rf-model-macro/src/lib.rs`, `crates/rf-validation-derive/src/generator.rs`, `crates/rf-validation-derive/src/lib.rs`, `crates/rf-macros/src/form_request_macro.rs`, `crates/rf-macros/src/simple_model.rs`, `crates/rf-macros/src/model_dsl.rs`, `crates/rf-db-facade/src/manager.rs`, `crates/rf-db-facade/src/query_builder.rs`

## Hard bets — feasibility

_This section is the honest, source-grounded verdict on the two most-requested "vision-literal" features. It supersedes the one-line summaries in **Rust feasibility limits** and **Tier 3** above with a concrete, tested account of what is real today, what can be cleanly added, and what fights the language. Grounded in `crates/rf-macros/src/lib.rs`, `crates/rf-macros/src/await_transformer.rs`, and the running probe `sandbox/probes/hard_bets_feasibility/` (asserts every claim below)._

### (a) Hiding `Result`/`Option`/`Ok`/`Err`/`Some`/`None`

**What already works (and how far it goes).** The framework ships a real, tested async-hiding layer — NOT a mock:

- `#[auto_await]` / `#[await_calls(..)]` (attribute proc-macros, `lib.rs:231/242`) walk a fn/impl/module AST and wrap each *name-matched* framework call (`find`, `all`, `create`, `get`, `put`, `send`, `dispatch`, … — the allow-list lives in `await_transformer.rs:35-116`) in a "maybe-await" adapter: `(&__rf_w(EXPR)).__rf_resolve().await`. Via autoref specialization (`await_transformer.rs:145-177`) the adapter **awaits the expression when it is a `Future` and passes it through unchanged when it is a plain value.** So one call site resolves correctly whether the underlying facade is sync (`Cache::get`) or async (`User::find`). A plain `fn` is auto-promoted to `async fn` when any call was wrapped (`lib.rs:320-330`).
- `rustforge!{ .. }` (`lib.rs:1018`) wraps a whole block, auto-applying `#[auto_await]` per fn and honoring a `#[sync]` opt-out marker (`lib.rs:1036`, a pure no-op marker consumed by the block expander) so a genuinely synchronous helper is left untouched.

**The probe proves the exact boundary:** in `sandbox/probes/hard_bets_feasibility/`, `handler()` calls `Cache::put`/`Cache::get`/`User::find`/`User::save`/`User::all` with **no `.await` anywhere**, and returns the correct value — `.await` is genuinely gone. But the same handler still writes `-> Result<i64, String>`, a `?` after **every** fallible call, `Ok(..)` at the tail, and `cached.unwrap_or(0)` to open the `Option`. That residue is the un-hidden half.

**Why `Result`/`Option` hiding is essentially unsolved (not merely unbuilt):**

1. **No uniform error type.** Auto-injecting `?` requires the enclosing fn to return a `Result` whose error type every wrapped call converts into. Real facades return heterogeneous errors (`String`, `CacheError`, `sea_orm::DbErr`, `anyhow::Error`). A body-rewriting macro that appends `?` would only compile if it also forced one lossy `Box<dyn Error>`/`anyhow::Error` return type — trading Rust's typed errors for stringly-typed ones. A wrongly-injected `?` on a non-`Result` value is a hard error surfaced at generated code, far from the user's source.
2. **Return normalization is ambiguous.** Wrapping a bare tail expression into `Ok(..)` means the macro must decide which tails are "the success value" vs. already-`Result` vs. `()` — early `return x`, `if`/`match` arms, and the trailing expr all differ. There is no sound, local rule; guessing wrong is a type error at a synthesized span.
3. **`Some`/`None` is not a macro problem at all.** Hiding `Option` means either a bespoke nullable value type (not `std::Option`) with accessor sugar, or silently unwrapping — which **masks real null-handling bugs**, the opposite of the framework's value proposition. A proc-macro over `std::Option` cannot change the fact that field access can't be fallible/`None`-shortcircuiting without `?`/`match`.
4. **rust-analyzer / type-inference cost is already paid even for the await-only layer.** The `(&__rf_w(EXPR)).__rf_resolve().await` wrapper obscures the call's type: hover/goto-def/completion degrade and inference errors point at adapter code. Extending the rewrite to errors/returns multiplies this: users would debug generated `?`/`Ok` they never wrote.
5. **Name-list matching is unsound by construction.** The allow-list is string-based, so a user's *sync, fallible* helper named `find`/`get`/`save`/`send`/`user`/`id` gets wrapped and awaited unexpectedly, and the list can silently drift from the real facade signatures. This is a *latent* footgun today and would compound if error handling were also name-driven.

**Cleanly-feasible subset (the honest recommendation):** keep hiding `.await` only; keep `?`/`Result` visible and typed. This is already shipped and green (`crates/rf-macros/tests/auto_await_sync_async.rs`, plus this probe). For error *ergonomics* — rather than *hiding* — the codebase already offers the honest, non-magic helpers: `rescue!(expr, fallback)` (`lib.rs:1291`, error→fallback value), `abort_if!`/`abort_unless!` (`lib.rs:1259/1271`), and `#[handle_exceptions]` (`lib.rs:1248`) which maps a handler's `Result` into an HTTP response so `?` is still written but its propagation terminates cleanly. These reduce visible error ceremony **without** faking that errors don't exist. No new code was added for this feature — inventing a `?`-injecting macro here would ship exactly the "compiles but lies / cryptic generated-span errors" failure the audit warns against.

### (b) Top-level `class`/`controller` keywords and `Controller@method` refs

**These are not "hard" — they are impossible in valid Rust outside a macro's own token stream.** Concretely:

- **`class Post { .. }` / `controller X { .. }` at module level do not parse.** Rust's grammar admits only a fixed set of item keywords at the top level (`fn`, `struct`, `enum`, `impl`, `mod`, `trait`, `const`, `static`, `use`, `type`, `macro_rules`, plus attributes/visibility). `class` and `controller` are not keywords and not items; the parser rejects them before any macro could run. There is no attribute, edition, or feature flag that adds a keyword — keywords are fixed by the compiler, not user-extensible.
- **Method bodies without `fn`/param lists (`store() { .. }` directly inside a `controller` block) do not parse** as Rust items either.
- **`Controller@index` is not an expression, path, or item.** `@` is only legal in Rust as a *pattern binding* (`x @ 1..=5`) and in a few attribute/macro-internal spots. In call/path position (`get("/", HomeController@index)`) it is a syntax error. The framework's real routing sugar therefore uses `Controller::method` tokens (see `routes!{}` in `laravel_macros.rs`, and the `model!`/`controller` examples), which the compiler *can* resolve to a real handler with goto-def and type-checking intact.

**The only path is macro-wrapping**, and the repo already takes it consistently:

- `model!{ Post => "posts" { .. belongs_to User via user_id, has_many Comment } }` (function-like proc-macro, `lib.rs:1787`) and `Model!(..)` (`lib.rs:460`) — the `belongs_to`/`has_many` "keywords" and the braced field DSL are legal **only** because they live inside the macro's `{ .. }` token group; the macro lowers them to a real `struct` + `impl`.
- `#[controller] impl PostController { .. }` (attribute macro, `lib.rs:151`) — a decorated *real* `impl` block, not a bare `controller` keyword. This is why the current form keeps IDE support.

**The probe demonstrates this positively:** `keywordish!(controller Post @ index)` accepts the keyword + bare-type + `@method` tokens verbatim *inside the macro invocation* and lowers them to an ordinary `fn index()`. The identical tokens written at module top level would not compile. That is the whole argument in executable form.

**Costs of the macro-wrapped route (the honest trade):** a `model!{}`/`controller!{}` function-like macro that *fully* mimics `class Post { .. }` loses IDE syntax highlighting and goto-def *inside* the macro body, makes any injected `request`/`Request` binding a synthetic identifier the user cannot re-type, and produces error spans pointing at generated code. The attribute-macro-on-real-`impl` form (`#[controller] impl X`) and `::`-based refs (`Controller::method`) keep all IDE affordances at the cost of literal vision fidelity.

**Recommendation (unchanged from Tier 3, now with evidence):** ship `::`-based real impls and `#[attr]`-on-real-item macros; do **not** chase bare top-level keywords or `@` — they cannot be made valid Rust, and the maximal function-like-macro emulation trades away the exact IDE/type guarantees that make Rust worth using over PHP. Reserve `model!{}`/`controller!{}` function-like wrapping for the cases where the braced DSL genuinely adds value (relationship keywords, column sugar) and accept `Controller::method`.

**Verification:** `cargo run` in `sandbox/probes/hard_bets_feasibility/` (green) asserts (a) `.await` is hidden while `Result`/`?`/`Option` remain, and (b) keyword+`@` syntax lowers only via a macro token stream. No production code changed for this feature — the finding is that hiding `.await` is the correct, already-shipped ceiling for (a), and macro-wrapping is the only path for (b).

Measured: a terse handler is **8 lines vs 34** for identical 201/422/404 behavior (~4× shorter). `AppError`/`AppResult`/`OrNotFound` are re-exported from the `rf` prelude.

## Second usage scenario — MediaFlow (upload + jobs + websockets) found the next layer (2026-07-09)

Following the TaskFlow lesson (a real app is the only honest audit), a SECOND app — **MediaFlow** (file upload → storage → background job → events → websocket broadcast → mail → cache → blade) — was built to stress the surfaces TaskFlow never touched. It built + tested green, but the adversarial passes again surfaced real bugs on the FAILURE paths. Fair credit first: **a lot was already solid** — cache (put/get/TTL/concurrency), the queue happy path (FIFO over 1000 jobs, 8 MiB payloads), storage (path-traversal-safe), upload error paths (clean 400s), websocket room isolation, blade (XSS-encoded), mail. These surfaces were more mature than the CRUD path had been. The bugs were in robustness/failure handling — all now fixed (commits `1c4e6f77`…`9e0cd494`):

- **Prelude `Result` shadow (blocker).** `rf::prelude` re-exported the 1-param `rf_errors::Result` alias, shadowing `std::result::Result` — so ANY `Result<T, E>` with a foreign error (e.g. a `Job::handle() -> Result<(), QueueError>`) failed to compile with a misleading `From<QueueError>` error. Every non-trivial app hit this on its first background job. FIXED: the prelude no longer re-exports bare `Result` (it exposes `RfResult` for the alias + keeps `RustForgeError`); bare `Result` is std again. No in-repo consumer relied on the alias.
- **Worker/queue robustness.** A panicking job unwound out of `work_once()`, was silently lost (already reserved off the deque), and KILLED the worker (one poison pill stopped all processing). FIXED: `catch_unwind` routes a panic through the retry/fail path; `fail()` now persists + a `Queue::failed()` accessor lists dead-lettered jobs; non-deserializable payloads dead-letter immediately (no retry storm); `reserve()` now honors `priority()` (FIFO among equals).
- **Event bus poisoning + deadlock.** `dispatch` held the global `RwLock` write guard while invoking listeners, so a panicking listener poisoned the lock (all later dispatch/listen panicked) and a listener calling back into the bus deadlocked. FIXED: snapshot listeners, drop the guard, invoke each under `catch_unwind`; recover from a poisoned lock instead of blind `.unwrap()`.
- **Multipart upload ceiling.** Uploads fell under axum's ~2 MiB default (while JSON got 10 MiB) and overflow returned a generic 400. FIXED: one consistent `MAX_BODY_SIZE` ceiling for multipart + JSON, oversize → **413**.
- **WebSocket robustness.** Subscribe sent no ack (remote clients had to race/sleep) and a lagging consumer was silently dropped on `RecvError::Lagged`. FIXED: send the `Subscribed` ack; survive `Lagged` (skip + continue, optional resync) instead of closing the socket.
- **Ergonomic gaps.** Added a process-global **`Broadcast` facade** (so a background job can broadcast statically like Cache/Mail/Event, no `Arc` threading), a **`Mail` one-liner** (raw text send without a `Mailable` struct), and a shipped **`examples/jobs-offline`** (rf-queue in-memory jobs with a Worker, no Redis — the offline path `jobs-demo` never showed).

**Verified:** `cargo check --workspace` default AND `--all-features` both **0 warnings**; crate tests rf-queue 23 / rf-events 20 / rf-event-facade 16 / rf-request 71 / rf-broadcast 19 / rf-mail 23 green; new probes (queue_job_result_shadow, queue_robustness, event_bus_panic_isolation, upload_size_cap→413, broadcast_ws_ack_resync, broadcast_facade_global) + regressions green; `jobs-offline` example test green.

**Standing verdict (reinforced):** two real apps → two batches of real bugs that source audits missed. The framework is materially more robust now — its failure paths (panics, poison, lost jobs, oversize bodies, dropped sockets) are handled, not just its happy paths.
